## 1. Component Version Selection

### Problem
Users need an easy way to choose between stable and latest versions of toolchain components (binutils, gcc, gdb, linux kernel, LLDB, .NET runtime).

### Analysis
- **LLDB and .NET Runtime**: Already handled. `package/lldb/Config.in` and `package/dotnetcore/dotnetruntime/Config.in` offer tarball (pinned) vs git (latest) choices with configurable version strings.
- **binutils, gcc, gdb**: These are Buildroot's built-in packages. Their version choices live in `~/buildroot/package/binutils/Config.in.host`, `~/buildroot/package/gcc/Config.in.host`, etc. — NOT in 4dotnet. We cannot modify these from the external tree.
- **Linux kernel**: Version set via `BR2_LINUX_KERNEL_CUSTOM_VERSION_VALUE` in defconfig.

### Decision: Multiple Defconfig Presets
Provide pre-built defconfig files representing different version strategies:

```
savedconfigs/arm64/
├── br2.defconfig           # Default: stable toolchain, LLDB=git/main, .NET=git/main
├── br2.defconfig.latest    # Everything latest
└── br2.defconfig.stable     # Everything pinned to known-good versions
```

**How users select:**
```bash
make BR2_EXTERNAL=~/4dotnet defconfig BR2_DEFCONFIG=~/4dotnet/savedconfigs/arm64/br2.defconfig.latest
```

**How users customize interactively:**
```bash
make menuconfig
# Navigate: Toolchain → GCC compiler Version → [choose]
# Navigate: Kernel → Kernel version → [choose]
make savedefconfig  # Save choices
```

### Implementation
- Create `br2.defconfig.latest` preset
- Document version selection in build docs
- Adding version choices to LLDB/.NET Config.in: DONE (Wave 2)

## 2. Adding Components to the Full Stack

### Current Stack
```
QEMU → Linux Kernel → LLDB / GDB → SOS (LLDB plugin) → .NET Runtime
```

### Proposed Additions

#### A. Boot Manager (U-Boot)
- **Why**: Realistic boot flow, kernel cmdline control, multi-boot support
- **How**: Enable in Buildroot menuconfig → Bootloaders → U-Boot
- **Impact**: ~10MB added to image, minor boot time increase
- **Priority**: Medium (optional — QEMU `-kernel` already works)

#### B. GDB SOS Plugin
- **Repo**: `https://github.com/oldzhu/gdbsos`
- **Why**: Complete the GDB side of the debugging story (LLDB has SOS already)
- **How**: New package `package/gdb-sos/` following existing LLDB SOS pattern:
  ```
  package/gdb-sos/
  ├── Config.in
  ├── gdb-sos.mk       # Clone repo, build, install .so plugin
  ├── config_gdb-sos.sh
  ├── build_gdb-sos.sh
  └── install_gdb-sos.sh
  ```
- **Dependencies**: `gdb-sos → gdb + dotnetruntime`
- **Priority**: High (completes the debugging stack)

#### C. .NET Diagnostic Tools
- **dotnet-trace, dotnet-counters, dotnet-dump, dotnet-gcdump**
- **Why**: Production-grade .NET diagnostics inside the VM
- **How**: Build from dotnet/diagnostics repo (already partially present)
- **Priority**: Medium

#### D. Profiling Tools
- **perf + FlameGraph scripts**
- **Why**: Kernel + userspace profiling for performance analysis
- **How**: Enable `BR2_PACKAGE_PERF` and add FlameGraph scripts to overlay
- **Priority**: Low

#### Decision
| Component | Decision | When |
|-----------|----------|------|
| U-Boot | Add as optional package | Next planning cycle |
| GDB SOS | Add as new package | Next planning cycle |
| .NET Diag Tools | Enhance existing diagnostics package | After GDB SOS |
| Profiling | Defer | After core stack complete |

## 3. AI / Agent Integration Strategy

### Three Options Evaluated

| | Custom Agent | Skills + Memories (Host Platform) | Hybrid |
|---|---|---|---|
| **Build effort** | High — new agent from scratch | Low — files in repo | Medium |
| **Maintenance** | You alone | Benefits from platform updates | Shared |
| **Distribution** | Users install separately | Comes with `git clone` | Skills in repo + optional custom agent |
| **Self-evolution** | Must build learning loop | Platform handles context, you curate knowledge | Best |
| **User experience** | Custom UX, learning curve | Familiar OpenCode UX | Familiar + specialized |
| **Depth** | Can call make/QEMU/LLDB directly | Limited by host agent capabilities | Skills for knowledge, custom agent for execution |

### Decision: Skills + Memories (Path B)

**Rationale**: The OpenCode skills/memories/plugins architecture already provides everything needed at zero distribution cost. Adding a custom agent would create maintenance burden without proportional benefit.

### Architecture
```
4dotnet/
└── .opencode/
    ├── skills/
    │   ├── build-4dotnet.md        # "build the ARM64 VM"
    │   ├── debug-4dotnet.md        # "start QEMU + LLDB/GDB debugging"
    │   ├── publish-4dotnet.md      # "publish .NET app to VM"
    │   ├── fix-build-error.md      # "diagnose and fix build errors"
    │   └── teach-4dotnet.md        # "teach user about the debugging stack"
    ├── memories/
    │   ├── project-knowledge.md    # What 4dotnet is, architecture, conventions
    │   ├── known-issues.md         # ARM illegal instruction, common errors
    │   ├── build-log.md            # Self-updating build results per user
    │   └── component-versions.md   # Track what versions work together
    └── agents/
        └── 4dotnet-builder.md      # Specialized builder persona (optional)
```

### Self-Evolution Mechanism
Each user's agent evolves independently:
1. User runs build → agent records result in `memories/build-log.md`
2. Build fails → agent reads error, checks `known-issues.md`, suggests fix
3. Fix works → agent appends solution to `memories/build-log.md`
4. Next build → agent references accumulated knowledge

Collective knowledge sharing: Users can PR their `memories/` back to the repo.

## 4. Distribution Model: From "Download Image" to "Build + Agent"

### Old Model
```
User: wget huge.tar.xz → extract → run QEMU → debug
You:  Build everything → package → upload to GitHub Releases
```
- 500MB+ downloads
- You rebuild for every update
- Images go stale

### New Model (Proposed)
```
User: git clone → agent guides → choose build/download → debug
You:  Maintain container + skills + package definitions + occasional pre-built images
```
- KB of config, not GB of images
- Always builds latest
- Agent self-evolves with each user
- Users learn the stack

### Decision: Hybrid Model
```
Path A: "I want it now"
  → Download pre-built base VM from GitHub Releases
  → Download optional debug pack
  → Start debugging immediately

Path B: "I want to learn / build / customize"
  → git clone 4dotnet
  → Agent helps configure + build
  → Agent self-evolves with your experience
  → Optionally contribute improvements back
```

This preserves the instant-gratification path while enabling the agent-assisted build path.

### Implementation Priorities
1. **Add OpenCode skills** — the agent interface (immediate)
2. **Maintain modular releases** — keep pre-built images current (periodic)
3. **Add GDB SOS package** — complete the debugging stack (next cycle)
4. **Create defconfig presets** — stable vs latest versions (next cycle)
